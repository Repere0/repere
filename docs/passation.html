Où en est le projet

II

Brief technique

pour un développeur JS / React

Premier réflexe attendu en découvrant le projet : « pourquoi ce n'est pas du React ? ». La réponse tient en quatre contraintes, et elles sont dures.

Les quatre contraintes qui décident de l'architecture

ContrainteConséquence directe
Hors ligne obligatoireL'app doit fonctionner sans réseau, dans le métro, dans un village sans couverture. Un fetch vers une API au premier rendu est disqualifiant.
Zéro donnée collectéePas de compte, pas de courriel, pas de mesure d'audience, une seule clé localStorage. C'est l'argument central du produit. Un serveur crée mécaniquement des journaux, donc des adresses IP.
Un développeur, ~8 h par semaineToute chaîne d'outils à maintenir se paie sur le temps de produit. Il n'y a pas de node_modules en production, pas d'étape de compilation.
250 € de budget totalAucun serveur applicatif. L'hébergement est statique et gratuit.
L'idée à retenir

Il y a un backend — il tourne au moment de la fabrication, pas de l'usage. Une action GitHub joue chaque matin le rôle qu'un serveur Express jouerait à chaque requête : elle collecte, normalise, vérifie, produit du JSON et publie. Zéro coût, zéro journal, zéro maintenance, et le résultat fonctionne hors ligne.

Pourquoi l'étape 10 est le verrou

Le banc ouvre le site reconstruit dans un vrai Chromium et mesure le rendu : hauteurs, contrastes, cibles tactiles d'au moins 44 px, absence d'erreur JavaScript, écrans qui ne s'ouvrent pas vides. Un seul échec et rien n'est publié. C'est ce qui rend acceptable une publication quotidienne sans relecture humaine. Principe de conception écrit dans le fichier : un banc vert sur une page cassée reste un banc vert — d'où la moitié des contrôles qui mesurent le rendu plutôt que de relire le texte du source.

Le RNE stocke les personnes par index dans deux tables globales — 7 821 prénoms, 74 728 noms. Le découpage réindexe ces tables par département : sans ça, chaque lecteur téléchargerait les 805 Ko de noms de France entière pour lire une commune.

Les huit invariants — ce qui fera échouer une contribution

  • 1. Autonomie. app_repere_vXX.html fonctionne hors ligne, sans une requête.
  • 2. Une seule clé. localStorage["repere.serie"], rien d'autre. Ni sessionStorage, ni IndexedDB, ni cookie.
  • 3. Aucun classement. Ni note, ni score, ni tri numérique d'une liste de personnes, de partis ou de territoires.
  • 4. Chaque chiffre porte sa source officielle et sa date.
  • 5. Doctrine du vide. Une absence produit une phrase et un lien — jamais un graphique vide, jamais un squelette animé.
  • 6. Rien qui gamifie le vote ou l'opinion.
  • 7. Palette. Cinq couleurs d'échelon figées ; hors échelons, aucune couleur ne dépasse une amplitude de canaux RVB de 24.
  • 8. Jamais le patrimoine d'un élu, jamais de donnée de présence ou d'absence.
Le piège le plus facile à déclencher

Le banc refuse toute adresse réseau contenant un code de commune — ?insee=13055, /donnees/13055.json. Un serveur qui sait quelle commune vous consultez sait où vous habitez. Le découpage est fait par département pour cette raison précise, pas pour la taille des fichiers.

Et React Native, alors ?

Question légitime, réponse nuancée — et il faut la poser dans cet ordre.

  • Réutilisable tel quel : tout l'étage données. Le pipeline, les schémas, les JSON produits. C'est du contrat, pas du code d'interface.
  • Non réutilisable : l'étage rendu, en totalité. Le fichier est du DOM impératif sans composants ; il n'y a rien à porter, il y a à réécrire.
  • Ce qu'une app native coûte ici : deux magasins d'applications, donc deux processus de validation, une identité de développeur, et des commissions de 15 à 30 % si un paiement apparaît un jour. Le web, lui, ne demande la permission de personne pour publier — ce qui, pour un produit civique en période électorale, n'est pas un détail.
  • Ce qu'elle apporterait : les notifications système. C'est la seule chose que le web ne fait pas bien sur iOS. Or le produit n'envoie aujourd'hui aucune notification, et l'arbitrage écrit dit qu'il ne notifiera jamais ce que l'utilisateur n'a pas fait.

Conclusion : le mobile natif n'est pas le prochain chantier. Il le deviendra le jour où il y aura des utilisateurs à qui il manque quelque chose — pas avant.

Pour prendre la main en dix minutes

# le dépôt
git clone https://github.com/Repere0/repere && cd repere

# faire tourner le banc sur le fichier de travail
npm install --no-save playwright && npx playwright install chromium
node test_repere.mjs app_repere_v18_19.html      # 40 contrôles, ~40 s

# reconstruire le site servi depuis le fichier autonome
python3 outils/build_pwa_reconstruit.py app_repere_v18_19.html site site_engendre

# la chaîne entière, telle qu'elle tourne en CI
bash outils/pipeline.sh

Convention de modification : on ne touche pas au fichier de 17 Mo à la main. Chaque changement est un script Python à assertions (outils/patch_NN_*.py) qui vérifie ses ancres avant d'écrire, puis le banc, puis la relecture des captures d'écran.
